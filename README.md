# RAG-система: Гарри Поттер

Лабораторная работа №1 — собственная RAG-система (Retrieval-Augmented Generation),
отвечающая на вопросы по семи книгам о Гарри Поттере на русском языке.

## 1. Описание проекта

Система принимает вопрос пользователя на русском языке и генерирует ответ,
опираясь **только** на текст семи книг о Гарри Поттере (перевод Росмэн), с
указанием источников (книга/глава) и защитой от выдумывания ответа, если в
тексте нет нужной информации.

Проект построен вокруг полного RAG pipeline: сбор данных → предобработка и
chunking → векторизация → retrieval → фильтрация → генерация ответа через
локальную LLM, — и в каждом компоненте проведены эксперименты по сравнению
альтернативных подходов (главный акцент лабораторной работы согласно заданию).

## 2. Архитектура

```
7 x .fb2 файлы (по книге)
        │
        ▼
   Grabber (fb2_parser.py + grabber.py)
   — парсинг XML, извлечение глав + метаданных, отслеживание изменений по хешу
        │
        ▼
   Chunking (chunking.py)
   — 3 стратегии: fixed_size / fixed_size_overlap / paragraph
        │
        ▼
   Embeddings (embed_store.py)
   — 2 модели x 3 стратегии = 6 FAISS-индексов
        │
        ▼
   Retriever (retriever.py)  →  top-K кандидатов
        │
        ▼
   [Reranker] (reranker.py) — опционально, по умолчанию ВЫКЛЮЧЕН (см. §10)
        │
        ▼
   Filtering (filtering.py)
   — threshold, дедупликация, отсечение коротких chunks, top-N
        │
        ▼
   Generation (generator.py, через Ollama)
   — system prompt с защитой от галлюцинаций + указание источников
        │
        ▼
   Streamlit UI (app.py)  /  консольный интерфейс (rag_pipeline.py)
```

## 3. Используемые технологии

| Компонент | Технология | Обоснование |
|---|---|---|
| Язык | Python 3.10 | стандарт для ML/RAG-разработки |
| Парсинг fb2 | `lxml` | надёжный XML-парсинг, книги хорошо структурированы (`<section>` = глава) |
| Embeddings | `sentence-transformers`, модели `intfloat/multilingual-e5-base` и `paraphrase-multilingual-mpnet-base-v2` | нужна мультиязычная поддержка (текст на русском) |
| Vector DB | FAISS (`IndexFlatIP`, косинусное сходство через нормализованные векторы) | локально, без сервера, подходит для учебного масштаба (~5000 векторов) |
| Reranker | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, `BAAI/bge-reranker-base` | протестированы обе, см. выводы §10 |
| LLM | Ollama (`qwen2.5`, `llama3`), локально | без платных API |
| Интерфейс | Streamlit | быстрый веб-UI без фронтенд-разработки |

## 5. Запуск

**Полный пайплайн с нуля** (из корня проекта, каждый шаг из своей папки в `src/`):

```bash
cd src/grabber
python grabber.py --raw-dir ../../data/raw --out-dir ../../data/processed

cd ../preprocessing
python chunking.py --processed-dir ../../data/processed --out-dir ../../data/processed

cd ../embeddings
python embed_store.py --processed-dir ../../data/processed --faiss-dir ../../data/processed/faiss
```

**Веб-интерфейс:**
```bash
cd src
streamlit run app.py
```

**Консольный режим:**
```bash
cd src/generation
python rag_pipeline.py --strategy paragraph --embedding-model intfloat/multilingual-e5-base --llm-model qwen2.5
```

## 6. Configuration

Ключевые параметры (передаются флагами командной строки или в сайдбаре Streamlit):

| Параметр | Значения | По умолчанию |
|---|---|---|
| `--strategy` | fixed_size / fixed_size_overlap / paragraph | `paragraph` (лучшая по метрикам, см. §10) |
| `--embedding-model` | intfloat/multilingual-e5-base / paraphrase-multilingual-mpnet-base-v2 | `e5-base` (лучшая по метрикам) |
| `--llm-model` | qwen2.5 / llama3 | `qwen2.5` |
| `--use-reranker` | флаг вкл/выкл | выключен (см. §10 — reranker ухудшает метрики на этом корпусе) |
| `--temperature` | 0.0–1.0 | `0.1` (низкая — для фактологических ответов, см. §11) |

## 7. API / внутренние интерфейсы

Система не имеет внешнего HTTP API — используется как библиотека Python. Основной класс:

```python
from rag_pipeline import RAGPipeline

pipeline = RAGPipeline(
    faiss_dir="data/processed/faiss",
    strategy="paragraph",
    embedding_model="intfloat/multilingual-e5-base",
    llm_model="qwen2.5",
    use_reranker=False,
)
result = pipeline.answer("Кто убил Дамблдора?")
# result = {"answer": "...", "sources": [...], "n_candidates_retrieved": 20, "n_chunks_used": 5}
```

## 8. Примеры использования

**Вопрос:** «Кто убил Дамблдора?»
**Ответ:** «Судя по контексту, Дамблдор был убит Снеггом. Это видно из фрагмента: "Струя зелёного пламени вырвалась из волшебной палочки Снегга и ударила Дамблдора прямо в середину груди." Источники: книга 6, глава 27 «Башня Молний».»

**Вопрос без ответа в базе:** «Какая начальная зарплата у профессора Хогвартса в галлеонах?»
**Ответ:** «В предоставленном контексте недостаточно информации для ответа на этот вопрос.» *(корректная защита от галлюцинаций — система не выдумывает цифру)*

## 9. Тестирование

Логика каждого модуля проверена юнит-тестами на упрощённых/синтетических данных
перед использованием на полном корпусе (`tests/`):
- `fb2_parser.py` — сверен на реальном файле (17 глав книги 1, автор/название/номер книги извлечены верно).
- `chunking.py` — все 3 стратегии проверены на корректность разбиения (размеры окон, overlap, границы абзацев).
- `embed_store.py` — построение/сохранение/загрузка FAISS-индекса и точность поиска проверены на синтетическом наборе.
- `filtering.py` — проверено удаление дубликатов, короткого текста, порога score на контрольном наборе кандидатов.
- `eval_metrics.py` — формулы Recall@K/Precision@K/MRR проверены вручную на контрольном примере с известным правильным ответом.

## 10. Результаты экспериментов

### 10.1 Chunking (на полном корпусе, 199 глав / 7 книг)

| Стратегия | Кол-во chunks | Средний размер (токенов) |
|---|---|---|
| fixed_size (500, без overlap) | 3705 | 488 |
| fixed_size_overlap (500, overlap 100) | 4609 | 487 |
| paragraph (~400) | 5104 | 354 |

### 10.2 Сравнение embedding-моделей x chunking-стратегий

Оценка на 19 из 30 вопросов eval-набора (с известным ground truth; остальные 11 —
`no_answer`-вопросы или случаи, где ни retriever не нашёл подходящий фрагмент
среди top-10 — см. §10.4):

| strategy | model | MRR | Recall@3 | Recall@5 | Recall@10 | Recall@20 |
|---|---|---|---|---|---|---|
| fixed_size | e5-base | 0.508 | 0.579 | 0.684 | 0.895 | 0.895 |
| fixed_size_overlap | e5-base | 0.492 | 0.579 | 0.737 | 0.789 | 0.895 |
| **paragraph** | **e5-base** | **0.592** | **0.632** | **0.737** | **0.947** | **0.947** |
| fixed_size | paraphrase-mpnet | 0.193 | 0.263 | 0.316 | 0.526 | 0.632 |
| fixed_size_overlap | paraphrase-mpnet | 0.214 | 0.211 | 0.421 | 0.579 | 0.579 |
| paragraph | paraphrase-mpnet | 0.184 | 0.158 | 0.316 | 0.368 | 0.579 |

**Вывод:** embedding-модель — решающий фактор (`e5-base` даёт в 2.5–3 раза более
высокий MRR, чем `paraphrase-mpnet`), потому что `e5-base` специально обучена с
асимметричными префиксами `query:`/`passage:` под задачу retrieval, а
`paraphrase-mpnet` оптимизирована под симметричную схожесть текстов. Среди
стратегий chunking'а `paragraph` — лучшая: естественные границы абзацев
сохраняют больше смысловой целостности, чем механическая нарезка по токенам.
**Финальный выбор: `paragraph` + `e5-base`.**

### 10.3 Top-K

Precision закономерно падает с ростом K (больше кандидатов — больше "шума"),
Recall растёт и выходит на плато к K=10–20 для лучшей комбинации. Средний
similarity score также монотонно снижается с ростом K на всех протестированных
вопросах — ожидаемое поведение.

### 10.4 Reranker — неожиданный результат

| Вариант | MRR | Recall@3 | Recall@10 |
|---|---|---|---|
| Baseline (только retriever) | 0.592 | 0.632 | 0.947 |
| + reranker `mmarco-mMiniLMv2` | 0.526 | 0.632 | 0.842 |
| + reranker `bge-reranker-base` | 0.440 | 0.474 | 0.842 |

**Обе** протестированные reranker-модели **ухудшили** метрики (MRR -11% и -26%
соответственно). Вероятная причина — **domain mismatch**: обе модели обучены на
задачах веб-поиска (MS MARCO / mMARCO — короткие запросы к веб-документам), а наш
корпус — художественная нарративная проза на русском языке. `e5-base` сам по себе
уже хорошо настроен под retrieval через асимметричные префиксы, поэтому
reranker'у "нечего добавить", а domain mismatch реранкера вносит только шум.
**Вывод: reranking — не универсальное улучшение, эффективность нужно проверять
эмпирически для конкретного домена. В финальной системе reranker отключён.**

### 10.5 Qualitative-наблюдения по retrieval (документированные ограничения)

5 из 30 вопросов не получили ground truth среди топ-10 результатов retriever'а
ни при какой из проверенных конфигураций:
- «Как называется вид спорта на мётлах?» (слишком общий/абстрактный вопрос)
- «Кто варил Оборотное зелье во 2 книге?» (retrieval не нашёл конкретную сцену)
- «Какого цвета галстук у Слизерина?» (визуальная деталь, упомянутая вскользь)
- «Кто был профессором ЗОТИ на 3 курсе?» (год обучения плохо разделяется семантически)
- «Почему Букля важна как символ?» (интерпретационный вопрос, ответ не сформулирован явно в тексте)

Также обнаружен интересный случай для вопроса про крестражи: слово "крестраж"
физически не встречается в тексте до 6-й книги, поэтому retriever не может найти
дневник Реддла (2 книга) по этому термину — ограничение семантического поиска,
не ошибка реализации.

**Вывод:** RAG на основе семантического поиска хуже справляется с точечными
визуальными деталями и абстрактными/интерпретационными вопросами, чем с
сюжетно-насыщенными фактологическими и причинно-следственными вопросами.

### 10.6 Генерация (LLM) и защита от галлюцинаций

Сравнение `qwen2.5` и `llama3` на одном и том же вопросе с одним и тем же контекстом:

| Модель | Результат |
|---|---|
| qwen2.5 (базовый промпт) | Верный ответ по сути, но перепутан номер книги-источника + утечка в китайский язык |
| llama3 | Отказалась отвечать («недостаточно информации»), хотя верный контекст был передан |
| qwen2.5 (усиленный промпт) | Верный ответ, верный источник, но добавлена выдуманная деталь («Сергей Вольдеморт») |
| qwen2.5 (усиленный промпт + temperature=0.1) | Верный ответ, верный источник, без выдумок, стабильно между запусками |

**Итеративный prompt engineering** (3 версии system prompt) + понижение
`temperature` с ~0.7 (по умолчанию у Ollama) до `0.1` устранили все три типа
ошибок: утечку языка, неточное цитирование источника и добавление
неподтверждённых деталей. Полная детерминированность не гарантируется ни при
каком temperature — это ограничение локальных LLM, которое стоит явно понимать,
а не пытаться полностью устранить.

## 11. Выводы

1. Выбор embedding-модели важнее выбора chunking-стратегии для качества retrieval — асимметричные, специально обученные под retrieval модели (`e5-base`) кратно превосходят модели общего назначения.
2. Reranking — не гарантированное улучшение; для нестандартных доменов (художественная литература) может ухудшать результат из-за domain mismatch между обучающими данными reranker-моделей и целевым корпусом.
3. Retrieval на основе векторного поиска систематически хуже справляется с абстрактными/интерпретационными вопросами и точечными визуальными деталями, чем с сюжетными фактами.
4. Защита от галлюцинаций LLM требует комбинации мер (явные правила в system prompt + низкая temperature) — ни одна мера по отдельности не устраняет все типы ошибок (выдумки, неточное цитирование, утечка языка).
5. Итоговая архитектура системы: `paragraph`-chunking + `intfloat/multilingual-e5-base` + retriever без reranker + фильтрация по threshold/дедупликации + `qwen2.5` с temperature=0.1.
